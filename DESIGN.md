# Design

## Key decision: one validation gate for every transaction

Transactions enter the program from two places, the keyboard and the CSV file, and both go through the same function, `build_transaction` in `validation.py`. It is the only code that creates a `Transaction`. The alternative was to check input in `cli.py` and trust the file when loading it, but a CSV can be edited by hand or in Excel, so it can contain the same mistakes a user can type. With a single gate, the rules cannot drift apart: changing what counts as a valid amount means editing one parser, and the prompts and the file loader both follow. It also keeps the other modules simple. `services.py` can add up totals without checking for negative amounts or unknown currencies, because an invalid `Transaction` should never reach it, and `frozen=True` prevents one from being changed by accident after it has been checked. This approach has two costs. Each typed answer is checked twice, once by `parse_field` so the user can correct it immediately and again when the full record is built. The program is also strict: if any row in the file is invalid, it lists the problems and refuses to open the file. That strictness is deliberate: each save rewrites the whole file, so continuing without the bad rows would silently delete them.
